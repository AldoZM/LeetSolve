subtitles:
  - You tap a button, and somewhere a server gets a note. What happens inside before you get an answer?
  - That note is a request. It says what you want to do, and to what.
  - Like this: get, slash players, slash Ren. Get is the verb. The path names the thing.
  - It can also carry headers, like your name tag, and sometimes a body with data.
  - Picture the server as a workshop. The note drops into a line of hoppers.
  - First, the router reads the verb and the path, and sends the note to the right worker.
  - On the way, it passes checkpoints called middleware.
  - One checks your name tag. No valid tag, and the note bounces back: four oh one, unauthorized.
  - Another counts your notes. Too many, too fast, and the golem stops you.
  - Then the handler, the worker who does the real job. He asks the database for Ren's row.
  - He writes the answer as jay-son, a simple text format: name Ren, emeralds twenty-five.
  - He stamps a status code on top, two hundred, OK, and sends it back. Often in a few milliseconds.
  - Now, rest. It's a common way to design these notes, so apps talk to servers the same way.
  - Everything is a resource with its own path. Players, orders, messages.
  - And a few verbs do the work. Get reads. Post creates. Put or patch changes. Delete removes.
  - Same path, different verb, different job.
  - The status code says what happened. Two hundred, it worked. Two oh one, created. Four oh four, not found. Five hundred, the server broke.
  - And the server doesn't remember you between notes. Each request brings everything it needs, name tag included.
  - That's what lets one server become ten identical ones, and any of them can answer.
  - So every tap is a note: a verb, a path, a few checkpoints, a worker and a stamped answer.
  - That's what a server does inside.
